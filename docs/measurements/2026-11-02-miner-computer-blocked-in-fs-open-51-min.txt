TWO THINGS THIS IS NOT

  The 17-turtle offline cluster is NOT the disconnect-cluster fault. All 17
  are marked offline inside 18 ms, which is one registry sweep by a server
  computer that had itself been frozen, not 17 radios failing. Counting this
  as an "8+ node episode" would be a false regression.

  It is NOT established as a fleet fault either. A CreateFile that does not
  return for 51 minutes is an operating-system level stall, and the sandbox
  host's G: drive is the first thing to rule out, not the Lua. Against that:
  the stall began while one miner was writing hard (five dump cycles in seven
  minutes, a sector reporting 2013 ores at one scan level, and every miner
  print is queued to disk by logship), and the previous run's gate check
  reported 537,458 bytes free on the server computer against the 1,000,000
  byte default limit. Those are reasons to look, not an answer.

WHY IT MATTERS BEYOND THE SANDBOX. A computer that blocks in fs.open does not
just lose itself: it held the ComputerCraft worker thread, and the Minecraft
server fell 61,430 ticks behind. One miner took the whole server down for 51
minutes. If this can happen on the live host it outranks every card currently
open, which is why it is written down rather than left in a run folder.

NEXT MEASUREMENT, FOR WHOEVER TAKES IT. Re-run the same scenario on the same
sector and see whether it reproduces; if it does, the ore count and the disk
figure are both testable (a sector with 2013 ores at one level versus an empty
one; a computer near its disk limit versus a fresh one). This run cannot
settle it: it is one occurrence, and I stopped the run rather than leave the
sandbox stalled.
